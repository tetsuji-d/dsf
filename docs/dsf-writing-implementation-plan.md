# DSF Writing 実装計画

### ReaderのWriting入口（2026-10-11 方針）

Readerのリード情報（i）ボタンの隣に鉛筆アイコン「書き込み / Writing」を実装した。`DSF_WRITING_PREVIEW=1` の開発・staging buildで、開いたportable v2／形式3のDSF、現在ページ、言語、見開きの配置をブラウザー内でWritingへ渡す。Readerへ戻る際はWriting付き形式3を検証して読み直し、ページ位置と筆跡を保持する。共有用DSFは閲覧できるが書き込みボタンを無効化する。HorizonのDL提供は未接続のため、配信版だけを開いた状態では書き込みボタンを表示しない。本番buildでは入口を出さない。今回の接続変更はローカル検証までで、まだデプロイしていない。

Writingのページめくりは前後ボタン・綴じ方向に対応した左右キー。タッチでは閲覧中1本指、書き込み中2本指のスワイプを使い、ペンの筆記はページ送りにしない。Readerの紙を曲げるアニメーションの共用は未実装。見開きをまたぐペン類の筆跡は、同じ軌跡を各ページの論理座標へ変換してページIDごとに保存し、各ページ枠でclipする。筆圧・筆幅・筆ペン輪郭を境界で作り直さない。1回の筆記を1つの履歴に確定するためUndo／Redoは左右まとめて行える。線・図形・文字は配置を開始したページ内で扱う。スキーマ変更はない。

2026-10-11追記: 現行Pressのportable v2を検証してWriting形式3コピーへ取り込む入口と、道具アイコン・小型画面用の下部操作／設定パネル／拡大切替を実装した。報告された18ページDSFで取込とWriting再保存を検証。互換取込の対象は現行v2と認定書体であり、旧v1への一般的な互換対応は含めない。実スマホ・OSキーボードの受入は引き続き未完了。詳細はUI検証記録を参照。

## 4 W0で固定する技術判断

- `formatVersion:3` と内部delivery schema 2の責務を分ける。archive manifest、Writing schemaの番号と許可entryを一覧化する。
- `base.json` のcanonical bytesとhash計算を同じ関数へ集約し、Horizon descriptor・portable・Writingが同じ原本を参照するfixtureを作る。
- 履歴の枝、削除、復元、共有用からの完全除去を契約化する。Undoで戻って再編集しても既存の枝を捨てない。
- 原本とWritingのフォントを分離し、横書き・縦書きの固定テキスト描画を再利用できる範囲を確定する。
- [仕様のカタログ採用方針](dsf-writing-spec.md#標準セット追加カタログの採用方針)に従い、オープンライセンスでも書体・版ごとに許諾を確認する。ライセンス変更や別版への更新を同じ認定として扱わず、取得済み原本のfont bytes・noticeを後から変更しない。フォント内フラグだけで許諾を自動判定しない。
- プロジェクトの書体管理を残したままリボンで適用する契約と、テキスト内で複数書体を使うrun表現を定める。Flow／Fixed／Writingの対応範囲を明示し、必要な作者データ形式変更は実装前に具体化する。
- Pressは原本全体、Writing編集用は全履歴の和集合、共有用は現在状態を対象にsubsetを生成する。Horizonの共有完全版とportableのsubsetに同じfont hashを要求する既存検証を、元書体の対応と描画等価性の検証へ置き換える。
- 字形の和集合をソートする前に、書体ごとの各runでNFC／NFDの字形も収集する。保存する文章自体は書き換えない。結合濁点を含む入力、横縦のメトリクス、ブラウザー実描画を比較する。W0で選んだ生成器は `harfbuzzjs 1.6.3` のsubset WASM。縦書き情報を欠く候補は採用しない。
- ブラウザー内で動くサブセット生成器を選び、Workerで実行する。WASM等の候補を比較し、可変WOFF2、縦書き、ライセンス、処理時間、メモリ、オフライン配布を確認する。Pythonの検証スクリプトをブラウザーでそのまま使えるとは扱わない。Writing本文をサーバーへ送る方式にはしない。
- 入力用完全版fontのアプリcacheと、各DSFの表示・履歴復元用subsetを分ける。完全版未準備の別端末でも既存表示・履歴復元ができ、新字形の入力だけは準備を必要とする導線を作る。
- 筆ペンの各点の幅と入力補正の保存契約、筆圧なしの補間方法を固定する。Reader本体とWriting資源のオフライン準備一覧を定義する。
- 履歴は本全体で直近30操作の一本へ統一（2026-10-14確定）。古い履歴だけを基準へ繰り込み、現在のobjectは保持する。object数、総points数、文字数、展開bytes、history bytesには別途安全上限を持ち、スマホ実機測定で見直す。

## 5 W3で固定する配信設計

既存のアップロードAPIはJSON／WebPの許可pathとサイズを厳密に検証する。これを任意ZIPアップロードへ緩めず、所有者・work・release・hashに限定したportable受付と取得経路を追加する。

APIで扱える最大サイズ、メモリ、タイムアウトを現在のCloudflare構成で確認する。ブラウザーの申告だけでZIPを `ready` にせず、サーバーでZIP構造・ファイルhash・同一版のページ／画像対応と、認定元fontからのsubset派生を検証する。完全版とsubsetのhash一致を要求しない。単一requestで安全に処理できないサイズや派生再検証は、上限を明示するかmultipartと非同期検証を設計する。実測・サービス制限を確認するまでは大容量公開を約束しない。

保管はアクセス制御可能な専用領域を第一候補とする。既存の公開media bucketに置くだけでは提供停止やprivateの制限が成立しない。Reader取得APIが現在の閲覧可否・DL提供可否を確認する。取得済みファイルやブラウザーに保存済みの原本は取り消せないことを仕様とUIで揃える。

公開時は、Horizon成果物とportableの検証receiptが揃ってからmetadata transactionを行う。ローカルWriting・履歴・個人の共有用コピーをアップロードAPIへ渡さない。原本の同時発行と個人Writingの保存は別の処理にする。

## 6 受入試験

| 対象 | 必須の確認 |
|---|---|
| 原本不可侵 | 各道具、移動、削除、Undo、復元、編集用／共有用保存のすべてで原本entryのbytesとhashが一致 |
| サブセット | 全言語、縦句読点、ルビ・圏点、異体字、結合文字、リンク番号、太さで元書体と字形・配置が一致。編集用の削除済み文字を復元でき、共有用ではその専用字形も残さない。原本subsetはWriting保存で変わらない |
| 追記と再保存 | subset未収録文字を準備済み完全版から追加して再生成できる。未準備の別端末では保存済み表示・履歴復元を維持し、新字形入力の準備不足を明示。完全版の不必要な重複同梱をしない |
| フォント選択 | プロジェクトの一覧がリボンに反映される。文字選択を失わず適用し、caret後の入力、混在選択、Undo／Redo、IME、読み込み失敗を検証。複数書体のDSP保存・Press出力・Writing保存で外観と範囲を維持し、未使用fontを同梱しない |
| カタログ・許諾 | 標準／追加で同じ採用条件を適用。許諾未確認と未ダウンロードを区別し、表示用subsetだけで入力候補を有効化しない。作者と別の認定書体でWritingを作成できる。完全版の準備失敗で既存文字や原本を置換しない |
| ライセンス同梱 | 通常版・編集用・共有用・別端末再保存で、収録fontに必要な本文・著作権表示・派生情報を保持。必要noticeの欠落や誤った対応を拒否。共有用の履歴削除でも必要noticeと原本bytesを保ち、改変時の予約名条件を確認 |
| 配置 | WebPと固定テキスト、縦横書き、単ページ／見開き、拡大、端末回転でも同じ位置に重なる |
| 入力 | マウス・タッチ・ペン、筆圧なし端末、IME、途中cancel、2本指。Writing中にページリンクや端タップが発火しない |
| 筆ペン | 筆圧による太細、筆圧なし入力、短い点・長い線・入り抜き。拡大率・再読込・編集用／共有用移送で筆跡形状を維持 |
| 履歴 | 削除・全消去・復元を取り消せる。過去へ戻って新編集した後も元の枝を復元できる。再読込・別端末への編集用DSF移送でも保持 |
| 共有用 | 消した秘密文字列が全ZIP entryに存在しない。履歴・未使用資源・個人認証情報を含まない。UI・コマンド双方で編集を拒否 |
| 通常版 | Writingを含まず、開いて新しく書き始められる。個人メモが通常DLへ混入しない |
| 永続化 | 容量不足、書込失敗、タブ競合、再起動で既存の保存済みデータを失わず、未保存状態を正しく表示 |
| 版の対応 | 同じworkの再発行、言語違い、同じページID、ファイル名変更を試し、違う版へ誤適用しない |
| 配信 | DLあり／なし、private・draft・限定公開・公開、提供停止、古いURL、部分失敗・再試行で権限と状態が一致 |
| オフライン | 準備後に通信を切り、ブラウザーを終了・再起動。表示に加え、全道具、新しい文字の入力、履歴復元、端末保存、編集用／共有用DSF書出し・再読込を外部取得なしで完了。準備不足・cache消去時に準備済みと誤表示しない |
| 不正入力 | unsafe path、二重entry、過大展開、壊れたhash、欠落font、履歴の循環を拒否し、原本だけを正常表示したふりをしない |
| UI | 390px幅とデスクトップ、日本語／英語、キーボード、画面外へはみ出さない道具・履歴UI |

共有用からの履歴漏れと原本bytes一致は自動試験にする。入力・ページめくり競合・スマホ操作・実ダウンロード・新規プロファイルでの再読込は実ブラウザーで確認する。build成功だけで受入完了としない。

## 7 切り替えと記録

形式3の生成・読込・配信APIを同じリリース単位で揃える。旧形式を必要とする試験作品は新仕様で再発行し、古いファイルを自動削除しない。過去Readerで新形式を表示する互換仕組みは作らない。

`docs/file-format-spec.md`、`docs/data-model.md`、`docs/pressroom-spec.md`、`docs/product-terminology.md`と必要な導入文書を実装に合わせて更新する。Project／DSP原稿の構造はWritingそのものの保存先にしない。PressのDL設定を作者設定として永続化する場合だけ、そのfieldと保存契約への影響を別途記載する。

ステージングでは架空原稿だけを使う。成果物ごとにcommit、形式version、公開URL、portable hash、確認した環境、操作証拠、未検証項目を残す。commit・ステージング反映・main統合・本番反映は、各時点のユーザー指示の範囲で実施する。今回の計画作成や以前のページリンクのデプロイ指示を、Writingの本番反映許可には使わない。

## 8 最初の実装単位

次に進めるのはW0とW1前半。最初に初期候補フォントの利用条件と配布元・版を確認して採用記録を作り、サブセット生成をブラウザー内・通信なしで試す。原本用・Writing現在用・Writing履歴用の字形集合を検証する。その後、架空の2ページ原本、ペン1筆、文字1件、削除・復元の履歴を持つ最小fixtureで、形式3の通常版／編集用／共有用を作る。共有用に削除した文章や履歴専用字形が残らず、必要なライセンス情報を保持し、3種類で原本bytesが一致するところまでを最初のレビュー単位にする。

この段階ではHorizonに公開せず、Readerの製品UIにも未完成機能を露出しない。ファイル契約が固まってから道具とHorizon導線を接続する。
