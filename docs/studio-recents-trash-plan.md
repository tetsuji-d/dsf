## 実装単位

### 1. エディターからのコピー削除（実装済み）

プロジェクト設定に入口を追加。Dashboardと同じ確認・削除・取り消し処理を使用。編集中の原稿を閉じてDashboardへ戻り、空のコピーは生成しない。保存実行中、原稿切り替え、共有編集の境界を守る。

### 2. クラウド原稿のゴミ箱（実装済み）

- サーバーが削除日時・復元期限・操作版を確定する。端末時計で期限を延長しない。移動・復元は再送しても二重処理しない。
- 原稿と既存の所属を保持し、通常の原稿一覧から除外。ゴミ箱に復元期限、所属、公開継続中の状態を表示する。
- 移動後は原稿の読み込み・保存・コピー・移動・再発行を制限する。開いたままの別タブ・旧クライアント・遅延中の保存もサーバーで拒否する。未送信内容を勝手に捨てない。
- 復元は期限内に限り、現在のアカウント状態と対象の権限・所属を再確認して原子的に実行する。権限を失ったスペースへ権限を再付与しない。
- Work/Release/public_projectsと公開用画像を保持。原稿をゴミ箱に入れた後も公開停止の管理導線を残す。復元で公開状態を変えない。
- 30日経過後は復元期限切れとする。物理削除は原稿と他のコピー・公開版で共有する参照を確認してから段階的に実行する。未実装のR2回収を「完全削除済み」と表示しない。
- 旧Firestoreとprivate R2の両経路が対象。共有原稿への適用では既存の役割権限と編集ロックを再確認し、権限を広げない。

必要なデータ契約は本文やDSP/DSF形式とは別のライフサイクル情報。既存原稿は情報がない場合に通常状態として扱う。

**権限ルール変更（2026-09-29 承認済み）**: 旧Firestore経路はクライアントから直接保存するため、UIだけでは旧タブの保存を止められない。ゴミ箱管理情報をサーバーだけが変更できること、ゴミ箱内・期限切れ原稿へ通常の本文保存を許さないこと、従来の完全削除で30日保持を回避できないことをRulesでも保証する必要がある。既存の閲覧者・編集者の範囲や公開閲覧の許可は拡大しない。Rulesの変更とステージング反映は、別途ユーザーの明示承認を得た。本番には反映しない。

検証: 旧/新保存方式、公開/非公開、権限失効、30日境界、移動/復元の再送、保存との競合、別タブの旧版、所属先変更、公開継続と停止、期限切れ、復元後の本文/画像の一致。実アカウント作品は削除せず隔離テストデータで行う。

今回の到達点: 本人所有の旧Firestore原稿とprivate R2原稿の移動・期限内復元、公開維持、別操作の公開停止、軽量一覧とゴミ箱画面を実装。共同編集のcanonical原稿は未対応として拒否し、権限を拡張しない。30日後の物理回収と、復元後の旧Firestore保存の一般的な競合対応は未実装。

### 3. スペース横断の最近の作業・検索（実装済み）

- 基本表示はアクセス可能な全スペース＋このブラウザーのコピー。「すべて / スペース / この端末のみ」で絞り込む。
- 同一作品を一つのカードにまとめ、所属、クラウド版、端末の未送信コピーを表示する。ただし内容は自動統合しない。
- 所有者UIDとprojectIdを照合する。タイトル一致やDashboardの選択だけで結び付けない。DSPから取り込んだ独立原稿は自動的に既存クラウド原稿へ結び付けない。
- 他アカウントに由来する端末コピーは、現アカウントのスペース作品として扱わない。
- 各スペースの権限確認済み一覧APIから軽量な項目だけを集める。権限のない題名を取得してからブラウザーで隠す方式にしない。本文は検索一覧のために取得しない。
- 表示件数・ページ送り・検索対象を明示し、未取得の作品まで検索済みと誤解させない。
- 「最近開いた」と「内容の更新日時」は別。全端末共通の最近の作業には、アカウント用の最終操作記録（作品IDと日時等）の保存契約を追加する。毎キー入力では書き込まず、開く・保存などの区切りにまとめる。
- 他端末のクラウド作品の操作履歴は共有できるが、未送信のローカル本文が端末間同期される意味ではない。オフラインや権限未確認の表示は明示する。

追加合意: アカウントごとに最大100件の作品ID・所属先ID・最終操作時刻を保存する方式を承認（2026-09-29）。openedを記録し、本文・ローカル専用原稿は送信しない。共有一覧は既存の限定公開範囲を維持し、未取得分を画面で明示する。

### 4. 端末版とクラウド版の再開・競合対応（次の単位）

- 時計だけで採用する版を決めない。復元・取り込み・端末時計の差でも日時が変わるため。
- 同一版と確認できた場合は一つの再開操作にする。端末だけに未送信編集があれば明示し、双方が変わっていれば二つの版を保持して選択・退避できるようにする。
- 先に旧Firestoreを含め基準版・内容ハッシュ・条件付き保存の契約をそろえる。保存方式変更は影響を説明して合意する。
- 自動マージは後続。本文だけでなくFixed Layout、画像、Flow構造、ページ順、削除の競合を扱えることが条件。更新日時の新しい方で単純上書きしない。
