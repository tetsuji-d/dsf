## 3. 実装順

見た目だけを先に全画面へ広げず、表示対象と状態を揃えたあと、同じ部品を順番に適用する。各段階で利用可能な状態を保つ。

| 段階 | 内容 | 主な対象 | 規模目安 | 次へ進む条件 |
|---|---|---|---|---|
| 0 | 現状監査・設計・受け入れ条件 | 本レビュー・本計画 | 今回 | 画面、用語、既存契約、未確認範囲が整理されている |
| 1 | 表示の正本・用語・移動先を統一 | Home、版一覧、保存文言、ヘルプ | 中 | 編集用リード／リーズを取り違えず、同じ版の状態とURLが一致 |
| 2 | 共通スタイルと編集用リードの縦一覧 | Home、最近の作業、共通部品 | 大 | 明暗・PC・狭い画面で一覧操作が成立 |
| 3 | リーズと版の詳細・公開操作 | edition reads／dialog | 中〜大 | 4フォルダ、対象版、確認、閲覧導線が一貫 |
| 4 | エディター・リード設定・プレス | editor work bar、settings、Press | 大 | 編集・保存を保ち、発行から公開設定まで迷わない |
| 5 | 補助画面・反応・全体文言の仕上げ | ごみ箱、復元、設定、help／PWA | 中 | 古い案内やテーマ差、重複導線が残っていない |
| 6 | stagingで通し確認・修正 | Studio→Horizon→Reader | 中 | 下記の受け入れ表を満たし、未確認事項が明記される |

規模は相対的なもの。所要時間は現状の未コミット変更の整理と、実画面での検証結果で変わる。並行して巨大な置換を行わず、段階ごとに差分をレビューできる形にする。

### 段階1：表示の正本・用語・移動先

1. Homeの編集用リード一覧、発行済み版、反応を別の表示モデルにする。版の一覧取得処理を表示部から切り離し、Home要約とリーズで共有する。
2. `isPublishedHomeWork()`／`getHomeWorkStatus()` による旧判定を新しい版管理の表示へ置き換える。古い編集用リードの `dsfStatus` を直して帳尻を合わせない。
3. 版数はedition state、題名・表紙・配信情報は対象版のsnapshotから取得。編集用リード一覧には編集用リードの現在情報を使う。
4. 選択中スペース、アーカイブ・廃棄・移行待ち、v1／v2を含む数え方を定義する。取得失敗は0ではなく未取得表示にする。
5. 左の「リーズ」を「編集用リード」へ。Home内の名前と共通ヘッダーの行き先を揃える。通常の一覧往復と「ダッシュボードを開く」を別の操作として扱う。
6. 保存・ファイル読込・発行・ヘルプの文言を、レビューの棚卸し表に沿って日英同時に修正する。読み上げ名とツールチップも対象。作品全体は「編集用リード」、Flow部分は「Flow原稿」、制作用の名前は「管理名」にする。
7. Flowの「原稿を開く」「連続原稿」「原稿言語」を「Flow原稿を開く」「Flow原稿」「原文言語」へ整理する。エディター内にある「原稿」を編集用リードへ一括置換しない。

主な既存ファイル：`js/app.js`、`js/home-workspace.js`、`js/edition-reads.js`、`js/edition-policy.js`、`js/i18n-studio.js`、`js/editor-work-bar.js`、`js/studio-work-status.js`、`js/studio-help-registry.js`、`js/flow-authoring-view.js`、`studio.html`。

完了条件：同じアカウント・スペース・版についてHomeとリーズの状態・タイトル・URLが一致する。v2が編集用リードの `dsfPages` 不在だけを理由に消えない。再発行で旧版の行やURLを上書きしない。

### 段階2：共通部品と編集用リードの縦一覧

1. Studio管理画面に限定した文字・余白・表紙・フォーム・ボタン・状態表示のルールを設ける。既存の `--studio-*` 色変数へ統一する。
2. 編集用リード一覧を、見出し・検索・範囲・並び順・行・ページ送りで構成する。最近の作業も同じ行部品を使う。
3. 初期表示25件、選択肢25／50件を目安にする。既存の取得済みデータをページ分割し、追加取得の有無を別に示す。表示のページ分割だけで通信量が減ったと扱わない。
4. 開いている編集用リードをコンパクトな作業バーにし、保存状態・編集へ戻る・必要な退避を維持する。ダッシュボードの大型統計カードを短い要約へ変更する。
5. デスクトップの固定列と狭い画面の縦積み行を用意する。題名の全文、その他操作、キーボードフォーカス、検索後の位置を確認する。
6. 既存の横棚用CSSとスクロールボタンを、使用箇所を確認して除去する。CSSの末尾に上書きを追加し続ける形を避ける。

主な既存ファイル：`js/recent-works-ui.js`、`js/recent-works.js`、`js/home-start.js`、`js/home-stat-card.js`、`js/app.js` のHome描画、`css/home-workspace.css`、`css/recent-works.css`、`css/studio.css`。

共通部品は表紙、行操作、検索・並び順、状態・空表示から始める。全面的なフレームワーク移行を前提にしない。共通スタイルを編集キャンバスやReaderへ無差別に適用しない。

完了条件：編集用リードを縦に比較でき、管理一覧の横スクロールがない。長い題名・画像なし・英語・ダークテーマで崩れない。既存の復元・権限・検索対象の制限を保つ。

### 段階3：リーズ・公開管理

1. 共通の一覧部品へ4フォルダを接続し、検索・作品絞り込み・発行日順を設ける。1行1版を維持する。
2. 通常行は題名／版名、状態、発行日、閲覧操作、その他だけにする。版名・後継版などは版の詳細へ移す。
3. 状態変更は対象版を明示する確認を通し、API成功後に移動する。キャンセル、通信失敗、競合、期限切れ、運営停止をそれぞれ表示する。
4. 公開／限定公開の閲覧リンクとURLコピーを同じ固定URL生成処理にする。非公開は所有者専用の指定版確認へ接続する。
5. アーカイブ・復元・廃棄の操作を整理する。廃棄の途中失敗は再試行可能な状態で表示し、物理削除完了前に「完了」としない。
6. 旧データの移行待ちは通常の読み取り可能な行として残し、利用できない操作に理由を示す。

主な既存ファイル：`js/edition-reads-view.js`、`js/edition-reads.js`、`js/edition-dialog.js`、`js/edition-policy.js`、`js/works.js`、`js/viewer-owner-preview.js`。公開側API・Rulesは既存契約を使い、見た目のために変更しない。

完了条件：非公開から公開／限定公開の確認でキャンセルすれば状態と選択が戻る。公開成功後のHorizon掲載有無とReader閲覧が一致する。URLは別内容へ再利用されない。

### 段階4：エディター・設定・プレス

1. 管理名・保存先・保存状態・主要操作を作業バーに整理する。公開タイトルは別の情報と分かるラベルにし、通常は長い説明を繰り返さない。
2. ページ選択の一覧と、実際に編集するページキャンバスを分ける。ページ順・綴じ方向・Flowグループ・リンク・IME・Undoの契約を維持して、縦型のページ選択を評価する。
3. リード設定を基本情報／言語／表紙と本文／保存と復元に分ける。項目の変更が即時保存か確定時保存かを統一した案内にし、現在の保存タイミングを黙って変えない。
4. プレスを「内容・言語の確認」「発行準備の結果」「書き出し／発行」に整理する。利用者が対処する警告は常時見せ、hash・ZIP・内部形式などは詳細へ分ける。
5. 開発用解像度・WebP容量比較試行は通常の発行操作から外す。利用可能な出力条件や検証ゲートを緩めない。
6. 発行完了では版名／発行日時・非公開状態を示し、「リーズで公開設定へ」で作成した版に焦点を合わせる。再試行時に意図せず新しい版が増えないかを確認する。

主な既存ファイル：`studio.html`、`js/app.js`、`js/editor-work-bar.js`、`js/studio-work-status.js`、`js/editor-viewer-preview.js`、`js/press.js`、`js/i18n-studio.js`、各リボン／設定パネルのCSS。

この段階は保存と編集への影響が大きいため、エディター全体の一括書き換えにしない。作業バー、設定、ページ選択、プレスの順に小さく適用する。

完了条件：既存編集用リードを開き、編集・保存・設定・プレスを往復して内容が保持される。編集用リードのプレビューと発行済み版の確認が区別できる。v1／v2双方の発行後導線が一致する。

### 段階5：補助画面と説明

- ごみ箱：管理名・復元期限・公開継続の有無を行で表示。公開管理は対象のリーズへ移動する。
- 復元用コピー：縦一覧、保存時点、対応先、保護した版の区分。大量の保護コピーにも検索・表示件数を設け、通常編集用リードへ自動統合しない。
- 反応：作品／版の単位、取得範囲、未取得を示す。現行APIで正確な総数を出せない項目は範囲付き表示または「—」にする。
- スペース設定：基本情報／メンバー管理を整理。表示範囲切替と所属変更を区別し、既存権限を拡大しない。
- ヘルプ：作る・保存する・発行する・公開する・復元するの順で分類。新しい文言と画面名に合わせる。
- ファイル／PWA／更新案内：`.dsfp`／`.dsfr` と旧入力の扱いを明記。通常画面での重複説明を減らし、オフライン準備の機能が完成したと誤認させない。

主な既存ファイル：`js/project-trash-ui.js`、`js/local-copy-delete-ui.js`、`js/publishing-spaces-ui.js`、`js/space-settings-navigation.js`、`js/space-members-settings.js`、`js/studio-help-registry.js`、`js/studio-install-guide.js`、`js/platform-install-copy.js`、`js/studio-pwa.js`、`js/studio-update-ui.js`、`js/studio-auth-save-status.js`。

完了条件：古い表現の検索結果を、現行UI・互換入力・開発内部名・歴史記録に分類できる。現行UIのボタンだけを直してエラーやヘルプが旧用語のまま残る状態をなくす。

### 段階6：stagingでの受け入れ確認

各段階のローカル確認後、対象差分と必要な配信設定を整理してstagingで確認する。本番・mainへの反映は別の明示指示を待つ。既存のユーザー作品では削除・廃棄の試験をしない。

## 4. 表示データの契約

| 表示するもの | 根拠 | 禁止する代用 |
|---|---|---|
| 管理名・所属・内容更新日 | 現行の権限確認済み編集用リード一覧と所属情報 | 公開版のタイトルだけで編集用リードを同定する |
| 保存状態 | 現在の編集用リード・編集revision・ファイル保存結果・クラウド保存結果 | IDBコピーがあることを「クラウド保存済み」とする |
| 発行済み版の題名・表紙・ページ・言語 | 指定Release／公開snapshot | 現在の編集用リードを古い版の内容として使う |
| 版の公開状態・アーカイブ・廃棄途中 | edition stateと既存の有効期間評価 | 編集用リードの古い `dsfStatus` だけを使う |
| 固定URL | edition IDまたは既存の固定binding | 再発行後の最新編集用リードURLへ付け替える |
| 件数 | 対象範囲・取得状況・数える単位が一致した集合 | 編集用リード数を版数、取得済み数を全件数とする |
| レビュー・反応 | 実際に取得できた作品単位の集計と取得範囲 | 作品合計を個別版の実績、失敗を0とする |

`js/edition-reads.js` は現在WorkごとにReleaseと状態を取得する。縦一覧への置換だけでは、この通信回数や全件取得の負担は変わらない。大量データ向けのサーバー側ページング・検索・集計は、必要な件数と負荷を測った上で別単位とする。最初の改修で存在しない集計APIや検索結果を捏造しない。

| ファイル | 新 `.dsfp`／`.dsfr`、旧 `.dsp`／`.dsf`、形式不正、保存キャンセル | 既存の内容検証を維持。新規保存は新拡張子。旧ファイルを黙って上書きしない |
| 発行 | 画像中心のv1・固定テキストを含むv2 | 新しい非公開版を作成。完了からその版の公開設定へ移動 |
| 確認 | 非公開→限定公開／公開、限定公開→公開 | 対象と公開範囲が分かる。キャンセル・通信失敗で不整合が残らない |

| 例外 | 期限切れ、運営停止、移行待ち、権限変更、アカウント変更 | 明確な理由。公開や読み取りの制限を回避できない |
| ごみ箱・復元 | 編集用リードの削除・復元、ブラウザーコピー削除 | 版の公開状態と編集用リードの状態が独立。復元の期限・影響が分かる |
| 取得失敗 | 一部スペース未取得、レビュー失敗、再読み込み失敗 | 「0」「何もない」と誤表示せず、再試行できる |

実機のタッチ確認と、PCブラウザーの幅変更による確認は別に記録する。まだ実機がない場合は未確認として残す。

## 6. 検証の進め方と既存資産

見た目だけの変更ごとに大量のテストを追加せず、状態・対象の取り違え、保存、公開の境界を重点的に検証する。

- 表示の正本：同じ入力に対してHomeとリーズの状態・件数・URLが一致する確認を追加する。全取得／部分取得／失敗も含める。
- 版管理：`scripts/verify-editions.js`、`scripts/verify-edition-uploads.js`、`scripts/verify-owner-draft-viewer.js`。Rulesに変更がある場合だけエミュレーター確認を含める。
- 編集用リード一覧・保存：`scripts/verify-home-dashboard-progressive.js`、`scripts/verify-project-display-title.js`、`scripts/verify-editor-save-status.js`、`scripts/verify-studio-leave.mjs`、`scripts/verify-studio-restored-reload.js`。
- 互換性：`scripts/verify-file-extensions.mjs`、`scripts/verify-project-trash.js`、`scripts/verify-publishing-spaces.js`。実際に変更した責務に合わせて選ぶ。
- UI：既存 `scripts/fixtures/edition-reads.html` を活用するが、fixtureだけで終わらせない。実StudioのCSSとナビゲーションで確認する。
- ブラウザー確認：行・ダイアログ・空／失敗状態・テーマ・幅を目視確認し、最後はstagingの実操作で検証する。

変更を適用するたびに、画面・状態・ローカル検証・staging実操作・未確認事項を区別して記録する。ビルド成功やHTTP成功だけでUIの完了としない。

## 7. 実装上の注意と残る判断

| 項目 | 扱い |
|---|---|
| 編集用リード一覧を初期画面にする | 推奨案。実装前の画面案で確認できるようにする |
| ページ選択を縦にする | 編集用リードの管理一覧より後。編集キャンバス・綴じ方向・既存の指操作を試してから適用 |
| 反応の集計 | 現在は作品単位。版別の分析を新たに提供する場合はデータ契約を別途決める |
| 大量の版・編集用リード | まず表示と取得範囲を明示。サーバー検索・集計の追加はUI変更と分ける |
| 複数選択と一括操作 | 初期段階に入れない。特に一括公開・廃棄は個別版での操作が固まってから検討 |
| 後継版・旧URL | 現在の合意を維持。自動リダイレクトをこのUI改修で導入しない |
| 保存・権限・ファイル形式 | 表示改善を理由に変更しない。必要性が判明したら対象と影響を分けて提案する |
| Reader／Writing | 閲覧の接続確認のみ。マージ済み道具バーの再設計を混ぜない |

まず実装する単位は、**「編集用リード／リーズ」の名前と表示対象の整理、公開状態の正本統一、Homeの縦一覧**。この単位で新しいStudioの基本構成を実画面で評価してから、リーズ、エディター、プレスへ広げる。
