# 出版スペースと保存先 — 第1段階

2026-09-21。ユーザーの実装開始指示に基づく、所有者による開設・切り替え・原稿所属整理。
課金、招待、共同編集、チャット、確認リンクはこの段階では提供しない。

## 個人アカウントと出版スペース

個人アカウントはログイン主体。出版スペースは作品を制作・管理・公開する単位。
名前は「出版スペース」とし、個人・サークル・企業で同じ仕組みを使う。
スペースは独立したIDを持つ。現段階は所有者のみアクセス可能。
所属変更は著作権・原稿の所有者・編集権・発行状態を変更しない。
将来の招待メンバーは別の明示的な権限モデルで導入する。

## 実装済みの操作

- 自分の出版スペースを作成、基本情報を設定、選択する。
- 自分のクラウド原稿をスペースへ所属させる／所属未設定へ戻す。
- 選択スペースに合わせてダッシュボードの原稿・発行済み作品・集計を絞り込む。
- 選択スペースからの新規プロジェクトは既存の保存処理を完了してから所属を登録する。
- 所属保存の失敗は原稿のクラウド保存成功とは区別する。所属未設定から再操作可能。
- エディターやWebMCP等、ダッシュボード以外から作った原稿はまず所属未設定。
- 空のスペースを開設しても既存作品を自動移動しない。
- ブラウザ内の選択履歴はアカウント別。ログアウト／切替時は一覧状態を破棄。

## 保存先の表示

1. **クラウド原稿** — ログイン中アカウントのサーバー保存原稿。出版スペースはこの原稿を整理する所属情報。
2. **このブラウザの作業コピー** — IndexedDBの最近の復元コピー。クラウド原稿の複製も含み、独立作品やクラウド保存成功の証拠ではない。
   既存の端末履歴はアカウント別ではないため、この一覧を「自分のクラウド作品」とは呼ばない。
3. **ファイルから開く (.dsp)** — 利用者が選択するファイル。ダウンロードフォルダーの自動一覧ではない。

ダッシュボードではクラウド原稿を先に表示し、作品分析を続け、端末コピーは折り畳む。
所属の変更でProject/Work/Release ID、公開URL、原稿、画像、R2保存先を変更しない。
DSP/DSFにアカウント権限や出版スペースの所属情報を追加しない。

## 永続化とAPI

サーバー専用の管理データ:
- publishing_spaces/{spaceId}: schemaVersion:1, ownerUid, name, profile?, createdAt, updatedAt。
- users/{uid}/publishing/catalogue: schemaVersion:1, revision, spaceIds[], assignments: {projectId:spaceId}。

全更新をFirestore transactionで行い、現在アカウント・所属・原稿の所有を検証する。
カタログは初期段階のowner index。32スペース／2,000関連付けを技術上限とする（課金枠ではない）。
所有権移転、削除済み原稿の関連付け整理、スケール時の個別索引化は別単位。
スペース削除・原稿移動・アカウント間移転は未提供。

GET /api/publishing-spaces は自己カタログだけを返す。
POST は create / rename / assign / profile / readImage。baseRevisionによる競合検知。
createはクライアント採番のspaceIdで重複作成を防ぎ、assignはexpectedSpaceIdも照合する。
実体の移動や本文書換えは行わない。同じ作成要求・同じ所属への再試行は冪等。
競合時は再取得して利用者に再操作を求める。勝手に上書きしない。

Firebase IDトークンと失効・無効化状態、ユーザードキュメントをサーバーで検証する。
現段階ではdisabledまたはmoderationHold中のアカウントを拒否する。
変更にはcanCreateProjectを必要とする。既存アカウントの権限は変更しない。
同一origin、メソッド、JSON、450KiB上限を検証し、レスポンスはprivate/no-store。
Firestoreクライアントからの新規管理パスへの直接アクセスは既存Rulesのデフォルト拒否に従う。
authoring用Firestore adapterの追加collection許可は、このサーバー処理だけが明示指定する。

- npm run verify:publishing-spaces

API障害からの再試行。実Studioの未ログイン表示も別途確認。

## 次の実装順と合意済み方針

1. 今回の基盤を実環境へ段階的に適用し、既存作品を所有者が整理する。
2. 招待・役割別権限と作品単位の単独編集権を導入してから、他アカウントの編集を許可する。
3. 最終編集30分経過、またはセッション失効で、権限のある別メンバーが合意なしで引継ぎ可能。
   自動的に担当者を交代するのではなく、引継ぎ操作を許可する。短い通信切断には猶予を置く。
   引継ぎ後の古い編集権による保存をサーバーで拒否し、未保存データを端末に保護する。
4. ダッシュボードの編集／閲覧メンバー表示、作品チャット、保存して交代する操作。
   一般読者・確認リンク閲覧者は内部メンバー表示／チャットに混ぜない。
5. 確認リンクは閲覧専用・最大180日。開いた時点の最新クラウド保存原稿を表示する。
   閲覧中の変更を勝手に反映せず、更新案内で読み直せる方式が候補。
6. スペース別使用量の計測・可視化、その後に課金。価格や容量の案は契約として実装しない。

読者は基本無料・広告なし。無料でもDSP/DSF書出しと自分でのファイル共有を維持する。
リアルタイム同時編集は当面対象外。

## 出版スペースの基本情報（2026-09-21）

個人プロフィールとは独立した設定。ユーザー指示に基づき、既存space schemaにoptional profileを追加。
基本情報ボタンから名前、概要（2,000文字）、Webサイト（HTTP/HTTPS）、
アイコン、背景画像を設定する。未設定の旧スペースも利用可能。

- プレビュー、画像の差し替え・削除、キャンセル、日本語／英語、スマホ幅に対応。
- 元画像はPNG/JPEG/WebP、20MiBまで。クライアントで中央切り抜き・WebP化。
- アイコン256×256、64KiB以下。背景1536×512、256KiB以下。
- 保存後の背景は表示幅に合わせて中央をトリミングする。位置調整は今後の拡張。
- profile: {description, website, icon:SHA256|null, banner:SHA256|null}。
  画像フィールド省略は維持、nullは削除。画像bytes/base64をFirestoreに保存しない。
- AUTHORING_BUCKETのpublishing-spaces/{uid}/{spaceId}/{sha256}.webpに保存。
  サーバーで実WebP形式・寸法・サイズを検証し、保存後に再取得してhashを検証してから関連付けを確定する。
- 画像取得は認証されたreadImage操作のみ。本人の所有確認・アカウント制限を通常一覧と同様に適用する。
- 管理画面でのみ表示。Horizonでの公開チャンネルページ／公開プロフィール反映は別工程。
- revision競合時は最新設定を表示して再編集を求める。設定編集中のrevisionを保存操作に使う。
- 画像はハッシュ別に保持。差替え・削除では参照を解除する。失敗時の未参照画像を含む物理削除は別途保守処理で扱う。
- この段階で画像を公開したり、他者のスペースへのアクセスを許可したりしない。

ローカルAPI＋Chromeで基本情報保存、画像WebP変換、再読み込み、削除、
キャンセル、別アカウントの画像取得拒否を検証。実R2/Firebaseへの接続検証・配備は未実施。

## ダッシュボード・保存接続の仕上げ（2026-09-21）

- Studio本体とブラウザ検証で同じ認証付き通信処理を使用する。
  セッション切替、応答のUID・所有者・schema・画像形式、応答サイズ上限を検証する。
- 出版スペースの応答を待たずにクラウド原稿／ブラウザ作業コピーを表示する。
  スペース取得完了後に表示範囲を更新し、その更新で再取得を繰り返さない。
- 一覧取得の古い失敗が、後から成功した保存状態を消さないようにする。
- 設定保存直後に応答を失った場合、同じ設定の再試行は書き込みやrevisionを増やさず成功を返す。
  その後に別の更新が入っていれば古い設定は競合で止める。
- 未有効・ログイン切れ・アカウント制限・変更権限・画像保存先の問題を区別して表示。
  画像取得失敗には画面内の再読み込みを設ける。未保存の入力は通常の通信失敗後も保持する。
- npm run verify:publishing-spaces-client: 実通信モジュールとAPIを接続して再試行・競合・セッション変更・応答上限を検証。
- npm run verify:publishing-spaces-local: ローカルworkerd/R2とFirestoreの実シリアライズ処理で
  画像保存／取得／破損検知を確認（認証およびFirestoreの通信先は検証用。クラウド接続の検証ではない）。
- verify:publishing-spaces-dashboard: 実dashboard rendererを実行し、スペース読込が未完了でも
  原稿一覧が表示されることを確認。新規原稿は保存成功後だけ所属を設定する。
- Chrome検証には応答消失後の再保存、別画面更新との競合、画像読み込み再試行を追加。

配備前提: stagingのAUTHORING_GOOGLE_SERVICE_ACCOUNT、FIREBASE_PROJECT_ID、
非公開AUTHORING_BUCKETは既存のauthoring API設定を使う。productionの機能は無効のまま。
実Firebase/R2への永続化・ログイン済みStudioのクラウド統合確認は、staging配備後に検証専用アカウント／スペースで実施する。

## 制作とHorizon発行の境界（2026-09-21）

- 出版スペース未所属でも、新規原稿作成・編集・ローカル／クラウド保存・DSP／DSF書き出しは利用可能。
- Pressの「Horizonへ下書き保存」は新しいReleaseを作るため、出版スペースへの所属を必須とする。
- Worksの下書き／非公開から公開・限定公開への変更にも所属が必要。
- 発行時に未所属なら選択ダイアログを表示。既存スペースを選ぶか、その場で名前を付けて開設する。
  原稿の所属を保存してから発行処理へ進む。キャンセルでは発行しない。原稿は変更しない。
- 既存の公開／限定公開作品は所属未設定でも閲覧を継続できる。
  同じReleaseの公開／限定公開切り替えや期間調整、非公開化を妨げない。
  新しいReleaseの作成や、非公開に戻した後の再公開には所属を求める。
- 既存作品はダッシュボードから後で所属を指定できる。自動移動・自動公開停止は行わない。
- 所属が設定済みなら選択操作を毎回求めない。発行時はサーバーの最新所属を確認する。
- 所属更新は従来のrevision／expectedSpaceIdを使用し、競合時は再取得して選び直す。
  応答消失後の再試行では同じ開設ID／更新条件を保持し、重複作成・勝手な上書きを防ぐ。

APIのread-only操作publicationContext(projectId, purpose: draft|publication)は、現在の作品状態から
所属が必要か、現在の所属先、自己カタログを返す。原稿・公開状態は変更しない。
private authoring APIは新規発行の準備前と確定transaction内の両方で所属を確認する。
旧Firestore保存経路にはRulesでProjectの新規Release／公開変更、public_projects書き込みの制約を追加。
カタログへのクライアント書き込みを許可しない。公開Viewerの読み取りルールは変更しない。

## 開設画面（2026-09-21）

## マイスペースの入口と保存先（2026-09-23）

出版スペースに割り当てていない本人所有のクラウド原稿を「マイスペース」として表示する。
初めて開くアカウントの表示先はマイスペース。以前に選んだ出版スペースや「すべてのクラウド原稿」は引き続き復元する。
切り替え一覧はマイスペース、所有する出版スペース、全クラウド原稿、参加しているスペースを区別する。
個人用の試作・ノート・写真集はスペース開設なしで作成できる。

内部では既存の `unassigned` 表示と `spaceId: null` の保存先を使う。Firestore/R2の原稿移行、新しいスペースレコード、権限変更は行わない。
マイスペース／全原稿からの新規作成は個人原稿として開始し、選択中の所有出版スペースから作成した場合だけ既存の保存・割り当て処理を使う。
コピーと保存先変更でもマイスペースを選択できる。共有参加者向けの新規作成は提供しない。

新規原稿は自動で公開しない。ただし既存の公開済み作品をマイスペースへ移しても公開は停止しない。
公開状態と共有権限は保存先とは別に管理する。既存原稿を一律に「非公開」と表示しない。
保存先一覧の読み込みに失敗した場合、別のスペースの作品をマイスペースとして表示せず再試行を案内する。
「すべてのクラウド原稿」は一覧障害時も本人の原稿を開くための入口として残す。

検証: verify:my-space-browser、verify:publishing-spaces-dashboard、verify-home-loading-browser.cjs、

### 後続の実装単位

1. マイスペースの作品単位の限定共有。閲覧／編集を明示し、作品への権限付与・解除を実装する。
2. 個人アカウントの「つながり」。既存の招待とベル通知を土台に、申請・承諾・解除を整える。
3. 共有先の選択でつながり一覧を利用する。つながりの成立だけでは作品への権限を付与しない。
4. 継続的な共同制作・公開は出版スペースで扱い、個人共有との境界を明示する。

上記は今後の計画であり、この単位では個人共有、友達一覧、個人チャットは提供しない。
