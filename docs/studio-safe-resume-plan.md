# 端末版・クラウド版の安全な再開 — 実装契約案

2026-09-29。対象: `feature/studio-local-pwa`、基点 `71afd6d`。両版保持と別プロジェクトへの切り分け方針は承認済み。基礎部品と隔離画面を検証。実運用の保存経路への接続は未実施。

## 現コードの確認

- `js/firebase.js` の `cacheLocalRecentProject` は `{state,imageMap}` を保存する。クラウドを読み込んだ時点の基準版を持たない。
- `loadLocalRecentProject` と起動時 `dsf_autosave` 復元は原稿の projectId を戻す。旧Firestoreでは、その後の編集が既存原稿の保存へ進みうる。
- private R2 の generation/revision と保存中リクエストは開いているセッションだけに存在する。基準不明の復元コピーからの保存は拒否される。
- 旧Firestoreはroot、v6 authoring/current、summary、Workをbatch保存する。読込時の内容と保存時の内容を条件付きで照合していない。
- `localRecentId` のクラウドキーは projectId のみ。アカウントをまたぐ同名ID、および同じ原稿の複数タブを分けて保持できない。
- 最近のコピー一覧は12件。単にここへ退避すると一覧から外れるため、競合コピーの保護先としては不十分。

## 到達する利用体験

Googleのオフライン編集を参考に、クラウドに所属する原稿は接続が切れても同じ作品として扱う。「この端末に保存済み・同期待ち」「同期中」「クラウドに保存済み」「変更の確認が必要」を表示し、版選択は通常操作ではなく衝突時に限ることを目標とする。ローカル専用原稿はクラウド保存先を選ぶまで同期対象にしない。

以下の第1段階は保護・判定の基礎整備であり、完成形の同期UXではない。元の作品への所属参照を保ちつつ、条件付き保存が未整備の経路では自動送信を停止する。端末用の別原稿として開く操作は、基準不明・権限失効・利用者が分離を選んだ場合などの退避手段とする。常に複製して版を選ばせる設計にはしない。

## 利用者向けの判定

比較の基準は更新日時でなく、原稿と素材の内容。クラウドの読込は現在の権限で行い、比較中にアカウント・原稿・内容が変われば結果を破棄する。

| 判定 | 条件 | 再開の扱い |
|---|---|---|
| 同じ内容 | 検証できた端末版とクラウド版が一致 | 最新クラウドを通常の読込経路で開く。比較結果から保存権限や基準版を作らない |
| 端末側に変更 | クラウドは基準と一致し、端末だけ変化 | 端末版を保護。条件付き保存対応後は同じ作品へ同期する。未対応経路では同期待ちとし、別原稿への退避も選べる |
| クラウド側に変更 | 端末は基準と一致し、クラウドだけ変化 | クラウドを開く入口を示し、端末版も残す |
| 双方に変更 | 両方が基準と異なる | 両版を保持。自動統合・自動上書きは行わない |
| 比較できない | 基準なし、権限未確認、画像不足、未対応形式、オフラインなど | 理由を表示。コピーを保持し、端末用原稿として再開できる範囲だけ許可 |

基準がなくても現在の両内容が完全一致なら「同じ内容」と判定できる。異なる場合、どちらが変更されたかは推測しない。

## 第1段階: 比較・保護・安全な再開

追加するのはブラウザー内の復元管理情報。DSP/DSFとクラウド原稿の形式は変えない。

- IndexedDBに原稿本体と分離した管理記録を置く。schemaVersion、認証先Firebase project ID、所有者UID、projectId、編集セッションID、基準の比較用指紋、対応する既存R2世代/版番号、基準取得方法を持つ。認証トークンやメールは保存しない。
- 比較用指紋はバージョン付き。本文・配置・ページ順・画像・トリミング・Flow・多言語・未知拡張を対象とし、UIの選択位置やズーム、公開状態、一覧用派生値を混ぜない。画像は検証済みの内容識別子を使い、blob URLの文字列だけで一致を判断しない。完全性が不明なら一致としない。
- 読込成功時、保存成功時にだけ、その成功したスナップショットに対応する基準を記録。保存中の追加入力を保存済みと扱わない。画像URL置換前後の指紋も対応づける。
- 別レコードに保護した端末コピーを残す。通常の12件の最近一覧とは独立して列挙でき、本人の削除操作まで期限・件数で自動削除しない。容量不足ならクラウドを開く前に停止し、DSP保存を案内する。画像参照を共有しても参照中の素材を削除しない。
- 同一projectIdでもアカウント・環境・編集セッションが違えば保護コピーを上書きしない。旧コピーは読めるままにし、基準不明として扱う。一括移行や起動時の削除はしない。
- 「最近の作業」「復元用コピー一覧」「起動時の復元」を同じ再開処理へ通す。対応するコピーがある状態でクラウドを直接開く場合も保護を先行する。
- 端末版を開いても、比較した最新revisionをそのまま保存基準へ採用しない。条件付き保存が未対応なら送信を停止し、元の作品との対応を残す。基準不明などで「別原稿として続ける」を選んだ場合は既存のローカル原稿分離処理を用いる。Horizon公開はクラウド側の保存確定を経由する。
- private画像は既存の認証済み画像経路を使い、取得できない素材を消して編集可能と表示しない。共同編集は既存のロック・回復処理を維持し、この段階では通常の端末コピー経路へ取り込まない。

## 第2段階: 同じクラウド原稿への条件付き保存

第1段階とは分けて契約を確定する。旧Firestoreを含む保存方式・権限ルールの変更は別途承認を必要とする。

- private R2は既存のCAS（基準版一致）を維持。指紋一致だけで最新revisionを採用して未送信内容を保存しない。
- 旧Firestoreでは、読込時の基準と実際の保存直前の基準をサーバー側で原子的に比較する。rootとv6子原稿が別版になる読込も防ぐ。
- 旧クライアントが条件を無視して保存できるままでは完全な競合保護とは呼ばない。条件付き保存を必須にする切替対象、古いタブへの更新案内、失敗時の原稿保持を先に定義する。
- 既存のowner境界、ゴミ箱、復元、移行、共有原稿の編集ロック、公開状態と原稿の分離を維持する。
- 権限を拡大しない。本番、main、Rulesの反映は承認範囲に従う。

## 検証項目

- 同一・片側変更・双方変更・同じ内容への収束・旧コピーの基準なし・画像不足。
- Fixedの位置/回転/切り抜き、ページ順・削除、Flow本文/構造、多言語、未知拡張の差を見落とさない。
- ローカル専用原稿とDSP取り込みをクラウドに勝手に結び付けない。
- アカウント変更、同名ID、別環境、同原稿の複数タブ、比較中の編集、保存中の追加入力、通信切断と復帰。
- 保護記録の保存失敗時は元のコピーも編集中内容も失わない。12件超でも保護コピーが見える。
- 比較だけでは本文のクラウド送信・公開・自動保存を発生させない。
- UIで比較→版選択→再編集→再起動→保護コピー再表示を確認。隔離データを使い、実ユーザー原稿を検証で上書きしない。

## Google公式情報から取り入れる設計（2026-09-29調査）

### 確認できた事実と限界

- 現行ヘルプはDocs/Sheets/Slidesのオフライン編集、再接続時の変更反映、変更履歴を説明している。また新しい変更が以前の変更を上書きすると説明する。衝突した二つの意図が必ず両立する、という保証ではない。端末の最終更新日時でファイル全体を単純選択する内部実装の証拠にもならない。
  - https://support.google.com/drive/answer/2375012?hl=ja
- Google Docsの技術者による2010年の記事は、文書を編集操作の履歴として扱い、各操作の基準revisionを把握すると説明する。端末は最後に受け取った版、未送信の変更、送信済み未確認の変更、現在の表示状態を区別する。
  - https://drive.googleblog.com/2010/09/whats-different-about-new-google-docs_21.html
  - https://drive.googleblog.com/2010/09/whats-different-about-new-google-docs.html?m=0
- 当時のDocsはOTで同時編集の位置などを変換し、全員の結果を一致させると説明する。一致することと、同じ箇所に対する両者の意図を完全に残せることは別。現在のSheetsのオフライン競合処理や保存方式の全詳細は今回の公開資料では確認できない。
  - https://drive.googleblog.com/2010/09/whats-different-about-new-google-docs_22.html

### DSFへの適用案（Google内部実装の断定ではない）

1. **同じ作品への安全な同期を先に実現する。** 原稿全体の保護コピー、共通基準、未送信状態、サーバーの保存確定応答を分ける。クラウドが基準版のままなら、端末側変更を既存の原稿へ条件付きで保存できる。片側変更の同期にはOT/CRDTの全面導入は必須でない。
2. **送信済み未確認を独立して扱う。** 応答が途切れたときは同じ保存要求IDで結果を照会・再試行する。成功確認前に未送信内容を捨てない。成功した送信の後で追加入力された内容は未送信のまま残す。R2の既存要求台帳とCASを活用し、旧Firestoreにも同等の保証を別途設計する。
3. **異なる場所の変更は後続で合成候補を作る。** 共通基準・端末・クラウドの3版を比較する。指紋だけでは編集差分を復元できないため、合成には基準本文のスナップショットまたは確実に再読込可能な版の保持が追加で必要。保存量・保持期間・権限失効時の扱いを合意してから追加する。
4. **合成の単位をDSFの構造に合わせる。** 安定IDを持つページ/Block、Flow段落、画像オブジェクトなどを候補にする。別ページの変更でも全体の綴じ方向・言語設定・ページ順・参照素材・Flow再配置に依存するため、単にIDが違うだけで安全とはしない。同じ画像の差し替えと切り抜き、削除と編集、順序変更は衝突として両版を残す。初期はプレビュー付きの合成候補とし、検証できた種類から自動化する。
5. **自由な同時編集はさらに後段。** 現在のUndoは最大50件のメモリー上スナップショットであり、同期用の永続操作ログではない。OT/CRDTを導入するなら、編集・Undo・画像処理・Flow・翻訳・自動処理を意味のある操作として記録する層が必要。ライブラリの追加だけで現在の全原稿スナップショットが自動統合されるわけではない。既存の共有編集ロックを先に外さない。

### 改訂した実装順序

- 4A: 復元情報・保護コピー・比較結果・同期待ち表示を整備。自動送信しない段階のUIを完成した自動同期と表示しない。
- 4B: 両保存方式の条件付き保存と再送安全性を整え、片側だけが変更された場合に同じ作品へ同期。安全を担保できる対象から有効化。
- 4C: 共通基準を使った構造別の合成候補とプレビュー。同じ場所の衝突は選択を求め、両方を保持。
- 4D: 必要性と負荷を評価して操作単位の共同編集を導入。OTかCRDTかは本文・画像・構造操作の要件で選ぶ。

後続のユーザー指示「その方針で進めて」により、両版保持・比較・別プロジェクトへ切り分ける実装を進める。基準本文の追加保持とクラウド保存方式・Rules変更は、具体的な契約を示して別途確認する。
## 切り分け方針と同時に扱う課題

- クラウド版を元の作品に残す場合、端末版は新しい作品IDで複製する。端末版を元に反映する場合、先にクラウド版の複製成功を確認し、選択後の再更新を条件付き保存で検出する。後者は第2段階まで公開しない。
- 複製は本文・画像・配置・作者を保ち、公開URL、Release、公開状態、共有権限を引き継がない。保存先のスペースにはその時点の作成権限を必要とする。
- 現行 `project-copy.js` はprivate画像参照の単純複製を拒否する。新原稿で利用できる画像実体・参照を用意して完全性を確認する必要がある。元原稿の削除後も複製を読めることを検証する。
- 保護保存失敗時は原本の切替・上書きを止める。コピー作成後に通信が切れた場合も、同じ要求の再試行で二重複製を避ける。
- 保護コピーはアプリが期限や件数で削除しない。ブラウザーのデータ消去や端末故障への備えにはDSP保存を併用する。既存の12件履歴とは独立して一覧・削除・取り消しを提供する。
- 同じ原稿の複数タブ・別アカウント・別環境を区別する。基準情報は作品の内容や公開ファイルへ混入させない。

## 4A 接続完了（2026-09-29）

ユーザーが保存・読込経路への段階接続を明示承認した後、以下を実装。

- 起動時のクラウド由来復元、最近の端末コピー、クラウド読込前、別タブから最近コピーが置き換わる場合に、原稿とその原稿が参照する端末画像を独立したIndexedDBへ保護。アカウントとFirebase環境で一覧を分け、期限・件数による削除はしない。同じ保護要求を内容で識別する。
- 最近一覧とエディターの「端末版を確認」から比較画面へ進む。共通基準がある場合は同一/端末変更/クラウド変更/双方変更を分類し、画像不足・通信失敗・基準不明は不明と表示する。日時だけで勝者を決めない。
- 「端末版を別プロジェクトとして開く」は新しい作品IDで端末保存し、成功後にエディターへ切り替える。本文・作者・固定配置を保ち、取得できた画像を独立した端末データへコピーする。公開URL・Release・共有権限は継承しない。画像実体が不足した場合は開かず、元の保護コピーを残す。再試行は同一ページセッション内で同じ複製IDを再利用する。
- クラウド版を開く操作は既存の所有者認証を使う。基準不明な復元から既存原稿を自動上書きしない。保存前に端末への保護が失敗した場合はクラウド送信も止める。通信失敗後の画面切替も、最新内容の端末保護成功が必要。
- 保護一覧に削除と取り消しを追加。クラウド原稿の30日ゴミ箱とは独立。
- `resume` と `resumeSession` は最近コピーの外側の情報であり、プロジェクト本文・DSP・DSFに追加しない。サーバースキーマ、Rules、公開状態は変更しない。
