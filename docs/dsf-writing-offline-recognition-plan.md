# Writing：オフライン認識と本全体の検索の検討

2026-10-14。設計案。認識エンジン・検索・DSF追加フィールドは未実装。既存の原本不可侵、ページ単位の管理、前後ページの先読み、本全体で直近30操作の履歴を維持する。

## 推奨する順序

1. **既存テキストの全ページ検索**。固定テキストページの `runs[].text` とWritingのテキストボックスを対象にする。ここにはOCRも追加モデルも不要。
2. **手書きへの文字情報の関連付け**。選択した複数の筆跡に、手入力した文字列を付けて検索・コピー可能にする。認識精度に依存せず使える基盤を先に作る。
3. **印刷文字の画像OCR**。Tesseract.jsをブラウザー内で動かし、画像ページを対象に精度・速度・容量を測る。
4. **手書きの画像認識を比較**。PP-OCRv5 mobileとNDLOCR-Liteを同じ日本語・英語・縦横書き・筆ペンの試料で比較。DSFのiPhoneブラウザーで動作・容量を確認してから選定する。
5. **フォント文字への変換**。関連付け済み文字から通常のテキストボックスを複製生成。元の筆跡を残すのを初期値とする。

## エンジン候補と現在確認できた範囲

| 候補 | 得意な入力／オフライン実行 | DSFへの適性と残る確認 |
|---|---|---|
| Tesseract.js + Tesseract言語データ | 印刷文字画像。WebAssemblyとWorker、言語データをローカル配置できる | ブラウザーOCRの最初の候補。Apache-2.0。日本語／縦書き用モデルも個別選定。公式FAQは手書きに不向きと明記しているため、手書きの主エンジンにしない |
| PaddleOCR PP-OCRv5 mobile | 日本語を含む画像文字。公式資料では英中の手書き・縦書きも強化 | リポジトリはApache-2.0。日本語手書きのDSF実用精度は未測定。ONNX変換・前後処理を含めてブラウザー版の試作が必要。選定した配布モデルの条件も固定して記録する |
| NDLOCR-Lite | 日本語資料画像。GPU不要のデスクトップ処理、v1.2から手書きを強化 | 日本語比較用の候補。CC BY 4.0に加え、現在の同梱モデルについて公式がDINOv3条件の遵守を要求。依存モデルの条件まで確認してから同梱を決める。標準配布はPython／デスクトップで、DSFブラウザー組込みは別検証 |
| Google ML Kit Digital Ink | 筆順・座標・時刻のある手書き。モデル準備後に端末内実行 | Android/iOS用。ブラウザー用の標準候補にしない。SDKは独自利用条件があり、OSSエンジンと同じ意味での「フリー」ではない。将来ネイティブ版を作る場合の比較対象 |

ここでの「オフライン」は認識中に画像・筆跡をサーバーへ送らないこと。初回のモデル取得は別であり、機内モードでも初回から使うには事前のオフライン準備が必要。無料のライブラリでも配布・学習済みモデルには条件がある。モデル未取得時に外部サービスへ自動で切り替えない。

現時点では全候補をDSFで実行・採点してはいない。公式の日本語対応や手書き対応だけで、日本語の崩し字・筆ペンへの精度を保証しない。ONNX Runtime Webは推論の実行基盤であり、それ単体が文字認識エンジンではない。

## 筆跡を残したまま文字を持つ

表示は現在のWritingオブジェクトをそのまま使い、別の「文字情報」を関連付ける。たとえば「おはよう」と書いた複数ストロークに `おはよう` を付けても、画面にフォント文字を重ねて表示しない。検索結果を選ぶと元のページへ移動し、対応する筆跡を一時的に強調する。

関連付けに必要な情報の案：

- 本の原本ハッシュ、言語、安定したpageId。
- 対象のobjectIds、対象筆跡の内容ハッシュ／版、文字情報の独立ID。
- 確定文字列、読み方向、文字列全体の領域。文字単位の正確な領域が得られる場合だけ追加する。
- `manual / OCR / ink` の由来、認識モデルIDと版、未確認／確認済み／要再確認の状態。信頼度はエンジンが返す場合だけ持つ。

行や語を単位に複数のストロークを関連付ける。一画ごとに文字として認識しない。最初はユーザーが対象筆跡を選択して「文字情報を付ける」を使う。範囲選択／複数選択のUIが前提となる。

認識候補は編集可能にし、確認して確定する。文字情報の修正は本全体の履歴に1操作として記録する。バックグラウンド認識の候補生成だけでは履歴を増やさない。移動は領域も追従、複製は新しいIDへ関連付けを複製、削除は検索対象から除外する。筆跡の形が変わった場合は要再確認とし、古い結果を確定文字として検索しない。処理中にUndoや削除が起きたら、対象の版が一致しない認識結果を採用しない。

現行の保存済み筆跡には座標・筆圧・太さ等はあるが、入力時刻の配列は保持していない。筆ペンの時刻は描画生成時に使い、保存形式では失われる。したがって当面は選択した筆跡だけを一時画像へ描いてOCRへ渡す方式が適する。元ページや他の注記を合成しない。筆順認識を採用する場合は、新規入力の時刻や筆順を保存する追加契約が必要で、既存筆跡から時刻を復元できるとは扱わない。

## 全ページ検索と軽量化

検索対象を「本文」「書き込み」「画像OCR」に分け、結果にはページ番号・抜粋・情報の由来を示す。ReaderとWritingで同じ検索UIを使う。

- 表示中ページのDOMだけを検索しない。全ページの固定テキストfragmentとWriting文字情報から、表示とは独立した索引を作る。
- 画像ページはStudio／Pressが元の文字列と確定位置を持つなら、将来は発行時にそれを検索用情報として出力する。文字情報のない既存DSFだけOCRする。
- 本文の正本は変更せず、検索用の正規化コピーと元位置の対応を持つ。全半角、英字大小文字、改行またぎを扱う。縦書きは見た目の左上順ではなく配信データの読み順を使い、ルビによる二重ヒットを整理する。
- ページ単位で文字情報を読んでWorkerへ渡す。表示の前後2ページの描画キャッシュとは別に、軽い検索索引をIndexedDBへ保存する。検索のために全ページの画像・フォント・DOMを一度に展開しない。
- 最初は文字列照合で実測し、大きな本で必要になったら日本語の部分一致に向くn-gram索引を加える。1文字検索は別経路を用意し、索引を全ページ数に比例して無制限に常駐させない。
- 未処理ページが残る場合は「検索可能 32 / 120ページ」のように範囲を表示する。未処理を含む0件を「本全体に存在しない」と誤表示しない。
- OCRは現在ページ／選択範囲優先、全冊は明示操作で逐次処理。中止・再開可能にし、低メモリー端末は同時実行1件から始める。ページ送りはOCR待ちにしない。

原本・書き込みの識別子、本文／筆跡の版、索引版、モデル版でキャッシュを識別する。Writing変更時は対象ページだけ更新する。削除した文字や以前の履歴の文字を現在の検索結果へ混ぜない。修正液は視覚的な上塗りであり、元の文字データを削除する機能とは扱わない。

## 保存とオフライン資源

認識モデルはアプリ側のオフライン資源としてバージョン固定で保持する。各DSFには入れず、DSFには文字列・領域・関連付けだけを保存する方向がよい。OCR用画像は一時生成し、通常はDSFに重複格納しない。モデル容量と実行中メモリーは別に測る。

文字情報は原本コンテナを書き換えず、Writing側の追加情報として保存する案とする。共有用は現在の確定文字情報だけを対象とし、履歴・削除済み文字・候補は同梱しない。共有用ロックは文字情報にも適用する。通常Readerで検索可能にするため、描画オブジェクトとは独立した読み取り経路を設ける。

現行バリデーターは未知フィールドを拒否するため、勝手にオブジェクトへ追加はできない。新しい付加情報の契約、保存・読込・履歴・共有時の扱いを合意してから実装する。検索索引は再構築可能な派生データとして、DSFへの同梱を必須にしない。

## 比較試験

同じ試料で日本語／英語、縦／横、ボールペン／筆ペン、崩し字、複数行、淡色、線や図形との混在を評価する。本文抽出・手入力の関連付けは完全一致で検証。OCRは文字誤り率、単語を検索できた割合、訂正に要した時間、初回／再実行時間、モデル取得量、ピークメモリーを記録する。PCと実機iPhoneを分け、機内モード・再起動後・キャッシュ不足・処理中ページ移動・Undo・DSF再保存再読込を確認する。

モデル選定は評価後とし、まずはエンジンに依存しない検索と文字情報の関連付けを作る。
